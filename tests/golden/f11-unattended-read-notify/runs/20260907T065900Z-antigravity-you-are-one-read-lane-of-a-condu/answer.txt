#### Finding 1: Unset variable fold falsely treats standalone variables before command punctuation as spliced
- **File & Line**: [core-guard.py:433](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L433)
- **What goes wrong**: In [fold_empty](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L399-L437), line 433 computes `alone = before in " \t" and after in " \t"`. When a standalone unset variable is followed by command separators or shell punctuation (such as `;`, `&`, `|`, `\n`, `(`, or `)` as in `cd $PROJECT_ROOT; rm -rf dist`), `after` is `';'`, failing `after in " \t"`. `drop_if_unset` misclassifies the variable as spliced into a word and strips it, turning `cd $PROJECT_ROOT; rm -rf dist` into bare `cd ; rm -rf dist`, which [_effective_cwds](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L303-L334) resolves to `$HOME` and [check_rm](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L925-L947) falsely denies.
- **Consequence**: Ordinary, safe build/cleanup commands chained with semicolons like `cd $PROJECT_ROOT; rm -rf dist` are falsely denied as destructive home-directory deletions.
- **Confidence**: 10/10

#### Finding 2: `command_views` does not compose `fold_empty` and `resolve_same_line_assigns`
- **File & Line**: [core-guard.py:511-524](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L511-L524)
- **What goes wrong**: [command_views](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L505-L525) generates [fold_empty(cmd)](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L399) and [resolve_same_line_assigns(cmd)](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L456) in parallel from the raw command string without ever chaining them. If a command combines a same-line assignment with an empty expansion (e.g., `V=r$1m; $V -rf ~` or `V=rm; $V -r$1f ~`), `fold_empty` leaves `$V` unresolved while `resolve_same_line_assigns` fails to match the unstripped token, leaving neither view with the executable dangerous command.
- **Consequence**: Destructive operations combining same-line variable assignments with empty positional or unset variable splices completely bypass detection.
- **Confidence**: 10/10

#### Finding 3: `check_db` misses destructive SQL when connection flags follow heredoc markers
- **File & Line**: [core-guard.py:1156](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1156) & [core-guard.py:1115](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1115)
- **What goes wrong**: In [check_db](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1119-L1159), line 1156 matches `seg_text in head`, where `head` from [heredoc_bodies_data](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1097-L1117) is sliced as `cmd[line_start : m.end()]` (stopping immediately at the heredoc marker `<<SQL`). When connection flags are placed after the marker on the same line (e.g., `psql <<SQL -h prod.example.com\nDROP TABLE users;\nSQL` or `mysql <<EOF --host=prod.internal`), `seg_text` contains `-h prod.example.com` while `head` does not, causing `seg_text in head` to evaluate to `False`.
- **Consequence**: Destructive remote database operations formatted with connection options after the heredoc operator bypass `check_db`.
- **Confidence**: 10/10

#### Finding 4: `check_db` naively splits on `|`, falsely classifying `||` (logical OR) as a pipeline
- **File & Line**: [core-guard.py:1136](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1136), [core-guard.py:1143-1147](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1143-L1147)
- **What goes wrong**: [check_db](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L1119) splits `cmd` with `cmd.split("|")`. When a command uses logical OR `||` (e.g. `echo 'DROP TABLE users' || psql -h prod.example.com -c 'SELECT 1'`), splitting on single `|` treats `echo 'DROP TABLE users'` as an upstream pipeline stage feeding destructive SQL into the database client.
- **Consequence**: Harmless commands that mention destructive SQL before a logical OR `||` connected to a safe remote query are falsely denied.
- **Confidence**: 10/10

#### Finding 5: `_shebang_shell` rejects `env -S` shebangs, causing scripts run by path to bypass inspection
- **File & Line**: [core-guard.py:570-574](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L570-L574)
- **What goes wrong**: [_shebang_shell](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L551-L575) splits the shebang line with `prog = first[2:].split()`. For scripts using `#!/usr/bin/env -S bash` (standard on macOS and Linux for shebangs with flags like `-euo pipefail`), `prog[1]` is `"-S"`. `os.path.basename("-S")` is not in `INTERPRETERS`, causing `_shebang_shell` to return `False` and [script_bodies](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L577-L674) to skip reading the script file.
- **Consequence**: Executable shell scripts using `env -S` shebangs and executed directly by path (e.g. `./cleanup.sh`) bypass the deletion inspection floor.
- **Confidence**: 10/10

#### Finding 7: `script_bodies` treats interpreter names in arbitrary argument positions as script launchers
- **File & Line**: [core-guard.py:624-645](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L624-L645)

For non-launcher utilities taking interpreter names or scripts as arguments (e.g. `grep bash evil.sh`, `diff bash evil.sh`, or `echo bash evil.sh`), `"bash"` is treated as the launcher for `"evil.sh"`, reading the file and passing its body to [check_rm](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L925).
- **Consequence**: Non-executing commands like `grep bash evil.sh` or `diff bash evil.sh` are falsely blocked whenever `evil.sh` contains a deletion statement.
- **Confidence**: 10/10

#### Finding 8: `check_history` misses space-separated `git reflog expire --expire now`
- **File & Line**: [core-guard.py:792](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L792)

#### Finding 9: `_under_system_root` fails on `/private/etc` and `/private/var` due to uncanonicalized prefix matching
- **File & Line**: [core-guard.py:85-95](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L85-L95), [core-guard.py:856-870](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L856-L870)
- **What goes wrong**: On macOS, `/etc` and `/var` are symlinks to `/private/etc` and `/private/var`. `/etc` is listed in `SYSTEM_DESCENDANT_ROOTS` while `/private` is in `SYSTEM_EXACT_ROOTS`. Because [_under_system_root](file://<home>/worktrees/20260907T065900Z-antigravity-you-are-one-read-lane-of-a-condu/hooks/core-guard.py#L856-L871) uses string prefix matching without resolving symlink equivalents, targets like `/private/etc` or `/private/etc/pam.d` match neither `SYSTEM_DESCENDANT_ROOTS` nor `SYSTEM_EXACT_ROOTS`.
- **Consequence**: Deletion of system configuration via `rm -rf /private/etc` bypasses the system root protection on macOS.
- **Confidence**: 9/10
